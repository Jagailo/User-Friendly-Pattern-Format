## 1. Введение

### 1.1. Что такое UFP

UFP — это *обратный шаблон*: шаблон описывает **форму искомого текста** —
последовательность статических литералов и именованных слотов-переменных, — а парсер
возвращает каждый слот как пару «имя → значение».

```text
значение: 04-05-2024_scan.jpg
шаблон:   <Date>_<Name>.<Extension>
результат: Date = "04-05-2024", Name = "scan", Extension = "jpg"
```

Шаблон состоит из частей двух видов:

* **статические части (сепараторы)** — символы, которые никогда не меняются и служат
  границами между значениями;
* **динамические части (переменные)** — именованные слоты в угловых скобках;
  переменную можно помечать как *жадную* звёздочкой на конце — тогда она захватывает
  как можно больше текста (`<Path*>/<Filename>.<Extension>`).

**Набор шаблонов** («mega pattern») перечисляет несколько альтернативных шаблонов через
`|`; парсер выбирает ту альтернативу, которая захватила больше всего переменных.

### 1.2. Зачем ещё один язык шаблонов

| | Регулярные выражения | Glob | Форматные строки / именованные шаблоны | UFP |
| --- | --- | --- | --- | --- |
| Пишется конечным пользователем | Сложно: кавычки, экранирование, группы | Просто, но без имён | Просто, но правила разбора не заданы | Просто, без экранирования |
| Именованное извлечение | Именованные группы с синтаксическим шумом | Нет | Да | Да — имя и есть слот |
| Жадность / нежадность | Явные квантификаторы, бэктрекинг | Только `*` | Обычно не определена | Одна `*` у переменной |
| Несколько форм в одном шаблоне | Альтернатива + якоря | Нет | Нет | Альтернативы через `|` |
| Детерминированный результат | Зависит от движка и бэктрекинга | — | Обычно не определён | Да — полностью определён ниже |
| Поведение при несовпадении | Возможен катастрофический бэктрекинг (ReDoS) | — | — | Полная функция, линейные проходы |

Принципы дизайна:

1. **Никакого экранирования.** Любой символ, кроме `<`, `>`, `|`, — литерал.
2. **Имена вместо групп.** Шаблон одновременно является схемой данных.
3. **Обратное сопоставление, а не валидация.** Парсер извлекает, но не проверяет
   содержимое переменных.
4. **Полная функция.** Любая пара (значение, шаблон) даёт результат; совместимая
   реализация не бросает исключений.
5. **Никакого бэктрекинга.** Границы находятся обычным поиском подстрок, стоимость
   предсказуема.
6. **Детерминизм.** При одинаковых входах все совместимые реализации возвращают
   одинаковый результат.

### 1.3. Область применения и что не входит

В области: синтаксис шаблонов, алгоритм разбора, модель результата, семантика
неуспеха, альтернативы, жадные переменные, проверка на соответствие.

Вне области: приведение типов извлечённых строк, валидация их содержимого (даты,
числа, e-mail), нормализация Unicode, локализация, формирование текста *из* значений,
потоковый разбор, формат сериализации результата.

### 1.4. Обозначения и термины

Ключевые слова **ДОЛЖЕН** (MUST), **НЕ ДОЛЖЕН** (MUST NOT), **СЛЕДУЕТ** (SHOULD),
**НЕ СЛЕДУЕТ** (SHOULD NOT), **МОЖЕТ** (MAY) понимаются так, как описано в RFC 2119.

| Термин | Значение |
| --- | --- |
| **значение** (value) | Текст, в котором ищут данные, например `04-05-2024_scan.jpg` |
| **шаблон** (pattern) | Одна альтернатива, например `<Date>_<Name>.<Extension>` |
| **набор шаблонов** (pattern set) | Список альтернатив через `|`, например `<A>_<B>\|<A>-<B>` |
| **часть** (part) | Один токен шаблона: сепаратор или переменная |
| **сепаратор** (static part) | Литерал, который должен присутствовать в значении; он вырезается |
| **переменная** (dynamic part) | Именованный слот `⟨имя⟩`, возможно жадный |
| **жадная переменная** | Переменная, имя которой заканчивается на `*`; захватывает до *последнего* возможного вхождения следующего сепаратора |
| **альтернатива** | Один шаблон из набора шаблонов |
| **карта результата** | Извлечённые пары «имя → текст» |

## 2. Модель данных и примитивные операции

### 2.1. Строки и символы

**Значение** и **шаблон** — конечные последовательности символов. *Символ* — один
элемент строкового типа языка: кодовая точка Unicode в языках с индексацией по
код‑поинтам (Python, Go, Rust `char`, Swift `Character`), единица UTF‑16 в языках с
индексацией по единицам UTF‑16 (.NET, Java, JavaScript). См. §10.1 — на результат это
не влияет.

Все сравнения **порядковые и регистрозависимые**: два символа равны, только если это
один и тот же символ, без свёртки регистра, без нормализации Unicode и без обрезки
пробелов. Значение никогда не изменяется функцией `Parse`.

### 2.2. Примитивные операции

Алгоритм из §4 и §5 записан через перечисленные ниже примитивы. Они определены
математически, чтобы спецификация не зависела от стандартной библиотеки.
`LENGTH(s)` — количество символов в `s`, индексы начинаются с нуля.

| Примитив | Результат |
| --- | --- |
| `LENGTH(s)` | Количество символов в `s`. |
| `SUBSTRING(s, from, to)` | Символы с индексами `from … to − 1`. `SUBSTRING(s, 5, 5)` — пустая строка. Требуется `0 ≤ from ≤ to ≤ LENGTH(s)`. |
| `CONCAT(a, b)` | Символы `a`, за которыми идут символы `b`. |
| `FIND(s, needle, start)` | Наименьший индекс `p ≥ start`, для которого `SUBSTRING(s, p, p + LENGTH(needle)) = needle`; `−1`, если такого нет. |
| `RFIND_WITHIN(s, needle, maxEnd)` | Наибольший индекс `p ≥ 0`, для которого `SUBSTRING(s, p, p + LENGTH(needle)) = needle` **и** `p + LENGTH(needle) − 1 ≤ maxEnd`; `−1`, если такого нет или если `maxEnd < 0`. |
| `TRIM(s)` | `s` без ведущих и замыкающих пробельных символов (Unicode `White_Space`). |
| `STARTS_WITH(s, prefix)` | `TRUE`, если первые `LENGTH(prefix)` символов `s` равны `prefix`. |
| `ENDS_WITH(s, suffix)` | `TRUE`, если `s` оканчивается на `suffix` (в частности `TRUE` при `s = "*"`). |
| `DROP_LAST(s)` | `s` без последнего символа; требуется `LENGTH(s) > 0`. |
| `SPLIT(s, ch)` | Список максимальных подстрок `s`, не содержащих `ch` (пустые подстроки включаются). |

> **Замечание о `RFIND_WITHIN`.** Это единственный неочевидный примитив. Верхняя
> граница — индекс **последнего символа**, который может входить в совпадение, а не
> индекс, с которого совпадение может начинаться: совпадение, начинающееся в
> `maxEnd`, **не** допускается, если его длина больше одного символа. На практике:
> `RFIND_WITHIN(s, needle, maxEnd) = s.rfind(needle, 0, maxEnd + 1)` (Python),
> `s.LastIndexOf(needle, maxEnd)` (.NET), `s.lastIndexOf(needle, maxEnd)` (Java,
> JavaScript). Если в языке есть только неограниченный обратный поиск, границу
> **НУЖНО** проверить явно — например, искать в `SUBSTRING(s, 0, maxEnd + 1)`.

## 3. Синтаксис

### 3.1. Зарезервированные символы

Особый смысл в шаблоне имеют ровно четыре символа:

| Символ | Значение |
| --- | --- |
| `<` | Начинает переменную. Внутри переменной игнорируется (отбрасывается). |
| `>` | Заканчивает переменную. Вне переменной игнорируется (отбрасывается). |
| `|` | Разделяет альтернативы набора шаблонов. Внутри шаблона встречаться не может. |
| `*` | Непосредственно перед закрывающей `>` помечает переменную как жадную. В любом другом месте — обычный символ имени. |

Все остальные символы — буквы, цифры, пробелы, пунктуация, эмодзи, любой символ
Unicode — обычные литералы, экранирование не требуется.

### 3.2. Корректные шаблоны

```ebnf
pattern-set = alternative, { "|", alternative } ;
alternative = { element } ;
element     = variable | static ;
variable    = "<", { name-char }, [ "*" ], ">" ;
name-char   = ? любой символ, кроме ">" ? ;          (* "<" отбрасывается, см. §4 *)
static      = static-char, { static-char } ;
static-char = ? любой символ, кроме "<", ">", "|" ? ;
```

Дополнительные правила:

1. `name-char` не включает `>`, потому что `>` завершает переменную.
2. `*` является меткой жадности **только** если это последний символ содержимого
   переменной *после* `TRIM`. `<A*>` — жадная переменная с именем `A`; `<A*B>` — не
   жадная с именем `A*B`; `<A *>` — жадная с именем `A ` (пробел сохраняется, потому
   что обрезка выполняется до удаления `*`).
3. Имя переменной **МОЖЕТ** быть пустым (`<>`). Пустое имя хранится в карте результата
   под ключом `""` и участвует в сопоставлении как любое другое имя.
4. Имя переменной обрезается `TRIM`: `<Date >` и `< Name>` — то же, что `<Date>` и
   `<Name>`.
5. `TRIM` влияет только на имя; извлечённый текст никогда не обрезается.
6. Статические части берутся буквально, включая пробелы.

### 3.3. Некорректные шаблоны

Токенизация (§4) — **полная функция**: она принимает любую последовательность символов
и никогда не завершается ошибкой. Поэтому в формате нет ошибки «некорректный шаблон».
Следующие конструкции некорректны по §3.2, но имеют определённый смысл:

| Конструкция | Смысл |
| --- | --- |
| `abc` (нет переменных) | Результат всегда пустой. |
| `<Date>_<Name` (незакрытая `<`) | Всё после незакрытой `<` становится статической частью; сама `<` отбрасывается. |
| `a>b<C>` (`>` вне переменной) | `>` отбрасывается; шаблон ведёт себя как `ab<C>`. |
| `<A<B>>` (`<` внутри переменной) | Внутренняя `<` отбрасывается; имя переменной — `AB`. |
| `|<A>\|\|` (пустые альтернативы) | Пустые альтернативы игнорируются (§6). |
| `<A><B>` (две переменные рядом) | Первая переменная игнорируется; последняя забирает остаток значения. |

Реализации **ДОЛЖНЫ** обрабатывать эти конструкции ровно так, как описано, и **НЕ
ДОЛЖНЫ** сообщать об ошибке. Авторам шаблонов **НЕ СЛЕДУЕТ** их использовать.

## 4. Токенизация

Токенизация превращает одну альтернативу (шаблон без `|`) в упорядоченный список
частей. Часть — это запись с тремя полями:

| Поле | Тип | Значение |
| --- | --- | --- |
| `text` | строка | Для сепаратора — литерал, который нужно искать. Для переменной — её имя (может быть пустым). |
| `kind` | `Separator` / `Variable` | Вид части. |
| `isGreedy` | логическое | `TRUE` только у переменной, имя которой оканчивалось на `*`. У сепараторов всегда `FALSE`. |

### 4.1. Алгоритм

```text
FUNCTION Tokenize(pattern) RETURNS List<Part>
    parts   ← пустой список
    inVar   ← FALSE
    buffer  ← ""

    ДЛЯ КАЖДОГО ch ИЗ pattern ЦИКЛ
        ЕСЛИ ch = "<" ТО
            ЕСЛИ НЕ inVar ТО
                inVar ← TRUE
                ЕСЛИ LENGTH(buffer) > 0 ТО
                    AppendSeparator(parts, buffer)
                    buffer ← ""
                КОНЕЦ ЕСЛИ
            КОНЕЦ ЕСЛИ
        ИНАЧЕ ЕСЛИ ch = ">" ТО
            ЕСЛИ inVar ТО
                inVar  ← FALSE
                name   ← TRIM(buffer)
                greedy ← FALSE
                ЕСЛИ ENDS_WITH(name, "*") ТО
                    name   ← DROP_LAST(name)
                    greedy ← TRUE
                КОНЕЦ ЕСЛИ
                AppendVariable(parts, name, greedy)
                buffer ← ""
            КОНЕЦ ЕСЛИ
        ИНАЧЕ
            buffer ← CONCAT(buffer, ch)
        КОНЕЦ ЕСЛИ
    КОНЕЦ ЦИКЛА

    ЕСЛИ LENGTH(buffer) > 0 ТО
        AppendSeparator(parts, buffer)
    КОНЕЦ ЕСЛИ

    ВЕРНУТЬ parts
КОНЕЦ ФУНКЦИИ
```

### 4.2. Свойства

* Текст любой части непуст **кроме переменной с пустым именем**; сепараторы никогда не
  пусты, потому что буфер выдаётся только при непустом содержимом.
* Два сепаратора подряд возможны только тогда, когда между ними в шаблоне стоит
  отбрасываемый символ, а две переменные подряд — только когда они стоят рядом
  (см. §3.3).
* Токенизация не смотрит на значение: это чисто синтаксическая функция.
* Токенизация **не** входит в горячий цикл типичного приложения: набор шаблонов можно
  разобрать один раз и переиспользовать для любого количества значений.

### 4.3. Примеры

| Шаблон | Части (`вид: текст`) |
| --- | --- |
| `<Date>_<Name>.<Extension>` | `V: Date`, `S: _`, `V: Name`, `S: .`, `V: Extension` |
| `<Path*>/<Filename>` | `V: Path (жадная)`, `S: /`, `V: Filename` |
| `pre/<A>` | `S: pre/`, `V: A` |
| `<A>_` | `V: A`, `S: _` |
| `<>_<B>` | `V: ""`, `S: _`, `V: B` |
| `<A><B>` | `V: A`, `V: B` |
| `<A *>` | `V: "A " (жадная)` |
| `<A*B>` | `V: "A*B"` |
| `<Date>_<Name` | `V: Date`, `S: _`, `S: Name` |
| `a>b<C>` | `S: ab`, `V: C` |
| `<A<B>>` | `V: AB` |

## 5. Сопоставление одной альтернативы

### 5.1. Модель

Пусть `P = p₀ … pₙ₋₁` — части одной альтернативы, а `S = s₀ … sₘ₋₁` — сепараторы среди
них в порядке шаблона. Пусть `V` — значение.

**Вхождение** сепаратора `x` — это индекс `p`, для которого
`SUBSTRING(V, p, p + LENGTH(x)) = x`.

Переменная `pᵢ` **завершается** частью `pᵢ₊₁`, если эта часть — сепаратор, либо
является **финальной** переменной, если за ней нет частей. Переменная, за которой идёт
другая переменная, **игнорируется** (§5.3).

Если шаблон начинается со статической части, эта часть — **требование к префиксу**:
значение **ДОЛЖНО** начинаться с неё, и она вырезается до нарезки первой переменной
(§5.3). Значение, которое с неё не начинается, не соответствует альтернативе вообще —
без этого правила ведущий литерал молча попадал бы в первое извлечённое значение
(`IMG_<Number>.jpg` извлёк бы `Number = "IMG_1234"` из `IMG_1234.jpg` и даже «совпал» бы
с `scan_99.jpg`). Любая другая статическая часть является терминатором стоящей перед ней
переменной, поэтому она обязательна и вырезается этой переменной.

Сопоставление — двухшаговый алгоритм:

1. **Найти сепараторы справа налево.** Сепараторы размещаются максимально правее,
   каждый строго левее того вхождения, которое выбрано для сепаратора справа от него.
   Именно это делает жадные переменные определёнными: их позиция конца известна ещё до
   нарезки.
2. **Нарезать значение слева направо.** Каждая переменная берёт текст между курсором и
   своим терминатором: *первое* вхождение терминатора начиная с курсора — для
   нежадной переменной, либо вхождение, найденное на шаге 1 — для жадной. Сам
   терминатор вырезается.

### 5.2. Шаг 1 — поиск сепараторов (справа налево)

```text
FUNCTION LocateSeparators(value, separators) RETURNS Array<Integer>
    positions ← массив из LENGTH(separators) элементов, все −1
    bound     ← LENGTH(value) − 1

    ДЛЯ k ОТ LENGTH(separators) − 1 ДО 0 ШАГ −1 ЦИКЛ
        positions[k] ← RFIND_WITHIN(value, separators[k], bound)
        ЕСЛИ positions[k] ≥ 0 ТО
            bound ← positions[k] − 1
        КОНЕЦ ЕСЛИ
    КОНЕЦ ЦИКЛА

    ВЕРНУТЬ positions
КОНЕЦ ФУНКЦИИ
```

Следствия:

* `positions[k] ≥ 0` означает «k-й сепаратор присутствует в значении целиком не позже
  чем за один символ до (k+1)-го сепаратора» — выбранные вхождения не перекрываются.
* Если сепаратор не найден в своей границе, его позиция `−1`, а граница не меняется,
  поэтому сепараторы левее ищутся в том же префиксе и могут быть найдены.
* Граница — индекс **последнего символа**, который может входить в совпадение; поэтому
  `RFIND_WITHIN` определён через `maxEnd`, а не через индекс начала (§2.2).
* Ведущая статическая часть не ищется через `RFIND_WITHIN`: она проверяется как префикс
  значения и вырезается (§5.1), а её элемент в `positions` не используется.
* Если `bound` становится отрицательным (сепаратор занимает начало значения, а левее
  ещё есть сепараторы), вхождение найдено быть не может: позиция `−1`. В этом случае
  **НЕ ДОЛЖНО** возникать ошибки.

### 5.3. Шаг 2 — нарезка значения (слева направо)

```text
FUNCTION ParseSingle(value, pattern) RETURNS Map<String, String>
    results    ← пустая карта
    parts      ← Tokenize(pattern)
    separators ← [ part.text ДЛЯ part ИЗ parts ГДЕ part.kind = Separator ]   (по порядку)
    positions  ← LocateSeparators(value, separators)

    segmentStart ← 0

    ЕСЛИ LENGTH(parts) > 0 И parts[0].kind = Separator ТО
        ЕСЛИ НЕ STARTS_WITH(value, parts[0].text) ТО
            ВЕРНУТЬ results                                # ведущая статическая часть не совпала
        КОНЕЦ ЕСЛИ
        segmentStart ← LENGTH(parts[0].text)                # ведущая статическая часть вырезается
    КОНЕЦ ЕСЛИ

    separatorsSeen ← 0

    ДЛЯ i ОТ 0 ДО LENGTH(parts) − 1 ЦИКЛ
        part ← parts[i]

        ЕСЛИ part.kind = Separator ТО
            separatorsSeen ← separatorsSeen + 1
            CONTINUE
        КОНЕЦ ЕСЛИ

        ЕСЛИ i = LENGTH(parts) − 1 ТО                       # финальная переменная
            results[part.text] ← SUBSTRING(value, segmentStart, LENGTH(value))
            CONTINUE
        КОНЕЦ ЕСЛИ

        ЕСЛИ parts[i + 1].kind = Variable ТО                # переменные рядом
            CONTINUE                                        # первая игнорируется
        КОНЕЦ ЕСЛИ

        terminator ← parts[i + 1].text

        ЕСЛИ positions[separatorsSeen] = −1 ТО
            ВЕРНУТЬ results                                 # неуспех, см. 5.4
        КОНЕЦ ЕСЛИ

        ЕСЛИ part.isGreedy ТО
            cut ← positions[separatorsSeen]
        ИНАЧЕ
            cut ← FIND(value, terminator, segmentStart)
            ЕСЛИ cut = −1 ТО
                ВЕРНУТЬ results                             # неуспех, см. 5.4
            КОНЕЦ ЕСЛИ
        КОНЕЦ ЕСЛИ

        ЕСЛИ cut < segmentStart ТО
            ВЕРНУТЬ results                                 # страховка, см. 5.4
        КОНЕЦ ЕСЛИ

        results[part.text] ← SUBSTRING(value, segmentStart, cut)
        segmentStart      ← cut + LENGTH(terminator)
    КОНЕЦ ЦИКЛА

    ВЕРНУТЬ results
КОНЕЦ ФУНКЦИИ
```

Замечания:

* Ведущая статическая часть проверяется и вырезается до начала цикла. Цикл всё равно
  учитывает её в `separatorsSeen`, когда доходит до неё, поэтому переменная после
  ведущей части завершается *следующим* сепаратором (`positions[1]`), а не ведущим.
  Позиция самой ведущей части (`positions[0]`) не используется.
* `separatorsSeen` — количество сепараторов, стоящих в шаблоне **до** текущей
  переменной; это же и есть индекс в `positions` того сепаратора, который **завершает**
  текущую переменную. Счётчик **ДОЛЖЕН** выводиться из частей шаблона, а не из числа уже
  извлечённых переменных (см. Приложение C).
* Переменная, которая не является ни финальной, ни завершённой сепаратором,
  игнорируется: она не даёт записи и не двигает курсор.
* Терминатор вырезается: `segmentStart` перескакивает за него.
* Финальная переменная всегда забирает остаток значения, включая текст, похожий на
  статическую часть шаблона. Терминатор убирается только у переменных, завершённых
  сепаратором.

### 5.4. Семантика неуспеха

У разбора **нет** единственного результата «успех/неуспех». Все переменные, извлечённые
до первой неудачи, сохраняются, поэтому результат частичного совпадения — это всегда
префикс переменных шаблона:

| Ситуация | Результат |
| --- | --- |
| Значение не начинается с ведущей статической части (§5.1) | Пустая карта: ничего не извлекается. |
| Сепаратор, завершающий переменную `v`, не найден на шаге 1 | Остановиться. Вернуть переменные, извлечённые *до* `v`. |
| Терминатор нежадной переменной отсутствует начиная с курсора | Остановиться. Вернуть переменные, извлечённые *до* `v`. |
| Найденная позиция разреза меньше курсора (страховочное правило; для значения, согласованного с шагом 1, недостижимо) | Остановиться. Вернуть переменные, извлечённые *до* `v`. |
| Ещё ни одна переменная не извлечена | Пустая карта. |

Поскольку набор шаблонов (§6) сравнивает альтернативы по числу захваченных переменных,
частичные результаты осмысленны: менее специфичная альтернатива побеждает только тогда,
когда более специфичная действительно захватила меньше.

Пустая карта означает «значение не имеет формы, описанной шаблоном». Непустая карта не
гарантирует, что шаблон совпал целиком.

## 6. Наборы шаблонов (mega patterns)

### 6.1. Разбиение

Набор шаблонов разбивается по каждому символу `|`. **Пустые фрагменты отбрасываются**,
поэтому `<A>|<B>`, `|<A>|`, `||<A>||` дают одинаковый список альтернатив, а набор,
состоящий только из `|`, не даёт альтернатив вовсе.

```text
FUNCTION SplitPatternSet(patternSet) RETURNS List<String>
    pieces       ← SPLIT(patternSet, "|")
    alternatives ← пустой список
    ДЛЯ КАЖДОГО piece ИЗ pieces ЦИКЛ
        ЕСЛИ LENGTH(piece) > 0 ТО
            APPEND(alternatives, piece)
        КОНЕЦ ЕСЛИ
    КОНЕЦ ЦИКЛА
    ВЕРНУТЬ alternatives
КОНЕЦ ФУНКЦИИ
```

### 6.2. Выбор

Каждая альтернатива сопоставляется независимо; возвращается результат той
альтернативы, которая захватила **наибольшее число переменных**. Число захваченных
переменных — это размер карты результата, поэтому повторяющееся имя считается один раз.

```text
FUNCTION Parse(value, patternSet) RETURNS Map<String, String>
    ЕСЛИ value = NULL ИЛИ patternSet = NULL ТО
        ВЕРНУТЬ пустую карту
    КОНЕЦ ЕСЛИ

    alternatives ← SplitPatternSet(patternSet)
    ЕСЛИ LENGTH(alternatives) = 0 ТО
        ВЕРНУТЬ пустую карту
    КОНЕЦ ЕСЛИ
    ЕСЛИ LENGTH(alternatives) = 1 ТО
        ВЕРНУТЬ ParseSingle(value, alternatives[0])
    КОНЕЦ ЕСЛИ

    best ← пустая карта
    ДЛЯ КАЖДОЙ alternative ИЗ alternatives ЦИКЛ     # строго слева направо
        current ← ParseSingle(value, alternative)
        ЕСЛИ SIZE(current) > SIZE(best) ТО          # строго больше: при равенстве остаётся первая
            best ← current
        КОНЕЦ ЕСЛИ
    КОНЕЦ ЦИКЛА

    ВЕРНУТЬ best
КОНЕЦ ФУНКЦИИ
```

Замечания:

* **При равенстве побеждает первая альтернатива**, поэтому порядок альтернатив значим и
  набор шаблонов детерминирован даже тогда, когда несколько альтернатив подходят
  одинаково хорошо.
* `SIZE` — количество записей карты результата (число различных захваченных имён), а не
  количество переменных в шаблоне.
* Альтернатива, которая ничего не захватила, даёт пустую карту и проигрывает любой
  альтернативе, захватившей хотя бы одну переменную.
* Проверки `NULL` и пустого набора — часть определённого поведения, а не детали
  реализации.

## 7. Модель результата

* Результат — **карта «имя переменной → извлечённый текст»**. И то и другое — строки.
* Ключи — это имена переменных ровно такими, как определено в §3.2 (обрезанные, без
  метки жадности). Имя может быть пустой строкой.
* Если одно и то же имя встречается в шаблоне несколько раз, **побеждает последнее
  присваивание** (`results[name] ← text` — это присваивание, а не вставка).
* Возвращаются только переменные. Статические части и число альтернатив в результате
  никак не отражены.
* Порядок записей карты не входит в спецификацию; потребители **НЕ ДОЛЖНЫ** на него
  полагаться.
* Никаких преобразований: `"10"` остаётся `"10"`, а не `10`; `""` — это захваченная
  пустая строка, а не «отсутствие значения». Отсутствие ключа — единственный способ
  выразить «не захвачено».
* Пустая карта — результат «ничего не захвачено»; она же используется и для значения, не
  соответствующего шаблону, и для шаблона без переменных.

## 8. Требования к реализации

Реализация **соответствует UFP-1.2**, если выполнены все условия ниже.

### 8.1. ДОЛЖНО (MUST)

1. `Parse(value, patternSet)` **ДОЛЖЕН** возвращать карту для **любой** пары входов; он
   **НЕ ДОЛЖЕН** бросать исключение, прерываться, выдавать предупреждение или
   возвращать `null`/`nil` — ни для какого значения или шаблона, включая некорректные
   шаблоны, пустые строки и сепараторы в самом начале или конце значения.
2. Результат **ДОЛЖЕН** совпадать с результатом псевдокода из §4–§6 для всех входов.
3. Сравнения **ДОЛЖНЫ** быть порядковыми и регистрозависимыми, без нормализации Unicode
   и без свёртки регистра (§2.1).
4. Значение **НЕ ДОЛЖНО** изменяться, обрезаться или нормализоваться.
5. Результат **ДОЛЖЕН** быть детерминированным: одинаковые входы всегда дают одинаковую
   карту.
6. Повторяющееся имя переменной **ДОЛЖНО** перезаписывать предыдущее значение (§7).
7. Альтернативы **ДОЛЖНЫ** перебираться в порядке следования, при равенстве остаётся
   первая (§6.2).
8. Аргументы `null`/`nil` **ДОЛЖНЫ** давать пустую карту (§6.2). Языки без `null` могут
   опустить это правило.
9. Частичные результаты **ДОЛЖНЫ** возвращаться так, как описано в §5.4.
10. Шаблон, начинающийся со статической части, **ДОЛЖЕН** совпадать только со значением,
    которое с неё начинается, и эта часть **НЕ ДОЛЖНА** попадать ни в одно извлечённое
    значение (§5.1).

### 8.2. СЛЕДУЕТ (SHOULD)

1. Токенизировать шаблон один раз и переиспользовать части для многих значений (§4.2).
2. Удерживать суммарную стоимость в пределах `O(|значение| · |шаблон|)` в худшем случае
   (§10.2).
3. Возвращать упорядоченную карту только как удобство; не документировать порядок как
   стабильный.
4. Дать способ отличить частичное совпадение, если язык это позволяет (например,
   отдельный метод, сообщающий число незадействованных частей) — но сам `Parse`
   **ДОЛЖЕН** сохранять заданную сигнатуру и семантику.

### 8.3. МОЖЕТ (MAY)

1. Добавлять типизированные методы (`ParseInt`, `ParseDate`, …) поверх `Parse`.
2. Кэшировать токенизированные шаблоны по строке шаблона.
3. Добавлять режим, в котором незакрытые переменные считаются ошибкой, — при условии,
   что поведение по умолчанию остаётся заданным.
4. Отвергать некорректные шаблоны только в отдельном, явно включаемом строгом API.

### 8.4. Безопасность

Бэктрекинга, рекурсии и исполнения шаблона как кода нет, поэтому формат нельзя
использовать для выполнения кода. Стоимость ограничена числом вызовов
`FIND`/`RFIND_WITHIN`: `O(число сепараторов)` обратных проходов плюс по одному прямому
проходу на каждую нежадную переменную, каждый линеен по длине значения. Набор шаблонов
умножает это на число альтернатив, поэтому даже шаблон с тысячами альтернатив стоит
лишь пропорционально больше — как и любой разбор, пропорциональный входу. Аналога
катастрофического бэктрекинга (ReDoS) здесь нет.

## 9. Каталог краевых случаев

Каждая строка входит в набор тестов на соответствие (§11) с тем же `id`.

### 9.1. Переменные, имена и метки жадности

| Шаблон | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `<Value>` | `any text here` | `Value = "any text here"` | Финальная переменная забирает остаток значения. |
| `<Value>` | `` (пусто) | `Value = ""` | Финальная переменная может захватить пустую строку. |
| `<>` | `abc` | `"" = "abc"` | Пустое имя допустимо. |
| `<>_<>` | `a_b` | `"" = "b"` | Повторное имя сохраняет последнее значение. |
| `<Date >_< Name>` | `04-05-2024_scan` | `Date = "04-05-2024"`, `Name = "scan"` | Имена обрезаются. |
| `<A><B>` | `ab` | `B = "ab"` | Переменная рядом с переменной игнорируется. |
| `<A*B>_<C>` | `1_2` | `A*B = "1"`, `C = "2"` | Жадность помечает только `*` на конце. |
| `<**>_<B>` | `1_2` | `* = "1"`, `B = "2"` | Одна завершающая `*` снимается. |
| `<A *>_<B>` | `1_2` | `A  = "1"`, `B = "2"` | Имя обрезается до удаления `*`, поэтому пробел остаётся. |

### 9.2. Жадные и нежадные разрезы

| Шаблон | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `<A*>.<B>.<C>` | `1.2.3.4` | `A = "1.2"`, `B = "3"`, `C = "4"` | Жадная берёт последнее возможное вхождение. |
| `<A>.<B>.<C>` | `1.2.3.4` | `A = "1"`, `B = "2"`, `C = "3.4"` | Нежадная берёт первое вхождение. |
| `<A*>_<B>` | `a_b_c` | `A = "a_b"`, `B = "c"` | Жадная сохраняет внутренний сепаратор. |
| `<A>_<B*>` | `a_b_c` | `A = "a"`, `B = "b_c"` | Жадная в конце шаблона. |
| `<A*>_<B*>_<C>` | `a_b_c_d` | `A = "a_b"`, `B = "c"`, `C = "d"` | Оба разреза ограничены следующим сепаратором. |
| `<A*>.<B>.<C>` | `1..2..3` | `A = "1..2"`, `B = ""`, `C = "3"` | Пустые сегменты допустимы. |
| `<A*>ab<B>` | `xabab` | `A = "xab"`, `B = ""` | Вхождение для `B` остаётся левее границы `A`. |
| `<A>ab<B>` | `xabab` | `A = "x"`, `B = "ab"` | Прямой поиск от курсора. |
| `<A*>aa<B>` | `xaaa` | `A = "xa"`, `B = ""` | Перекрывающиеся вхождения двухсимвольного сепаратора. |
| `_<A*>_<B>` | `_a_b_c` | `A = "a_b"`, `B = "c"` | Ведущая статическая часть вырезается и не смещает терминатор жадной переменной. |

### 9.3. Статические части: требование к префиксу и якоря

| Шаблон | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `pre_<A>` | `pre_abc` | `A = "abc"` | Ведущая статическая часть обязательна и вырезается. |
| `pre_<A>` | `zzz_abc` | *(пусто)* | Ведущая статическая часть должна быть префиксом значения. |
| `IMG_<Number>.jpg` | `IMG_1234.jpg` | `Number = "1234"` | Ведущая часть не попадает в извлечённое значение. |
| `IMG_<Number>.jpg` | `scan_99.jpg` | *(пусто)* | Значение с другим префиксом не извлекается вовсе — именно это делает шаблон пригодным как фильтр, в том числе внутри набора шаблонов. |
| `<A>_<B>_` | `1_2` | *(пусто)* | Замыкающая статическая часть должна находиться, а её нет. |
| `<A>.<B>.jpg` | `x.png.jpg` | `A = "x"`, `B = "png"` | Замыкающая часть служит якорем для `B` и вырезается ею. |
| `<A>.<B>.jpg` | `x.png` | `A = "x"` | Частичный результат: `.jpg` отсутствует. |
| `<A>.jpg` | `x.png` | *(пусто)* | Первая же переменная неуспешна. |
| ` <A> _ <B> ` | ` x _ y ` | `A = "x"`, `B = "y"` | Пробелы — обычные статические символы; захваченный текст не обрезается. |

### 9.4. Порядок, пустые сегменты и границы

| Шаблон | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `<A>_<B>` | `_` | `A = ""`, `B = ""` | Оба сегмента могут быть пустыми. |
| `<A>_<B>` | `_x` | `A = ""`, `B = "x"` | Значение начинается с сепаратора. |
| `<A>_<B>` | `x_` | `A = "x"`, `B = ""` | Значение заканчивается сепаратором. |
| `<A>_<B>` | `no separators at all` | *(пусто)* | Терминатора нет. |
| `<A>_<B>.<C>` | `a.b_c` | *(пусто)* | Сепараторы должны идти в значении в том же порядке, что и в шаблоне. |
| `<A>_<B>_<C>` | `_x` | *(пусто)* | Сепаратор в позиции 0 не оставляет места сепараторам левее. |
| `<A>_<B>_<C>_<D>` | `_x_y` | *(пусто)* | То же правило, на уровень глубже. |
| `<A>.<B>.<C>` | `.x.y` | `A = ""`, `B = "x"`, `C = "y"` | Цепочка помещается, поэтому пустой первый сегмент допустим. |
| `<A>_` | `x_` | `A = "x"` | Замыкающий сепаратор, завершающий переменную, вырезается. |
| `<A>_` | `x` | *(пусто)* | … и он должен существовать. |

### 9.5. Наборы шаблонов

| Набор шаблонов | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `<A>\|<B>` | `x` | `A = "x"` | Равенство: побеждает первая альтернатива. |
| `<A>_<B>\|<A>` | `1_2` | `A = "1"`, `B = "2"` | Побеждает альтернатива с большим числом переменных. |
| `<A>_<B>\|<A>-<B>` | `1-2` | `A = "1"`, `B = "2"` | Первая альтернатива не захватила ничего, вторая — две. |
| `<A>_<A>\|<A>` | `1_2` | `A = "2"` | Повторное имя считается один раз, поэтому обе дают по одной переменной; побеждает первая. |
| `\|<A>\|` | `x` | `A = "x"` | Пустые альтернативы отбрасываются. |
| `\|\|` | `x` | *(пусто)* | Альтернатив нет. |
| `` (пусто) | `x` | *(пусто)* | Альтернатив нет. |

### 9.6. Unicode и регистр

| Шаблон | Значение | Результат | Почему |
| --- | --- | --- | --- |
| `<a>_<B>` | `Abc_def` | `a = "Abc"`, `B = "def"` | Имена регистрозависимы. |
| `<A>_<B>` | `Abc_def` | `A = "Abc"`, `B = "def"` | Сепараторы сравниваются с учётом регистра. |
| `<A>→<B>` | `x→y` | `A = "x"`, `B = "y"` | Сепаратором может быть любой символ. |
| `<A>_<B>` | `привет_мир` | `A = "привет"`, `B = "мир"` | Кириллица — обычный текст. |
| `<A>_<B>` | `🙂_🙃` | `A = "🙂"`, `B = "🙃"` | Символы вне BMP сохраняются целиком. |
| `<A>…<B>` | `x…y` | `A = "x"`, `B = "y"` | Многобайтовые сепараторы совпадают точно. |

## 10. Замечания по реализации

### 10.1. Единицы кода и кодовые точки

`LENGTH`, `SUBSTRING`, `FIND` и `RFIND_WITHIN` можно реализовать над единицами UTF‑16
(.NET, Java, JavaScript), над байтами UTF‑8 (Go, Rust) или над кодовыми точками (Python).
Это **не** меняет результат, потому что каждый индекс в алгоритме — граница сепаратора:

* все индексы, которые возвращает `RFIND_WITHIN`, — начала вхождений сепараторов, а
  каждый сепаратор — целая последовательность символов;
* `segmentStart` всегда равен `cut + LENGTH(terminator)`, то есть тоже границе символа.

Следовательно, разрез никогда не может разделить суррогатную пару или многобайтовую
последовательность. Единственное требование — использовать **одну и ту же** единицу
последовательно внутри реализации.

### 10.2. Сложность

Пусть `n = LENGTH(value)`, `m` — длина шаблона в символах, `s` — число сепараторов,
`a` — число альтернатив.

| Этап | Стоимость |
| --- | --- |
| Токенизация одной альтернативы | `O(m)` |
| Поиск сепараторов | до `s` обратных проходов, каждый `O(n·L)` для терминатора длины `L` |
| Нарезка значения | не более одного прямого прохода на переменную, каждый `O(n·L)` |
| Набор шаблонов | сумма по `a` альтернативам |

Худший случай — `O(n · m)` на набор шаблонов (при `s ≤ m` и `L ≤ m`); это тот же порядок,
что и наивный `Split` по каждому сепаратору, и никакого комбинаторного взрыва.
На практике именно обратные проходы шага 1 делают жадные переменные дешёвыми: позиция
конца каждой жадной переменной известна до копирования текста.

Типичные оптимизации, не нарушающие соответствие:

* токенизировать наборы шаблонов один раз и кэшировать части;
* искать только в оставшемся префиксе (`maxEnd`) — спецификация этого и требует; не
  сканировать значение заново, когда граница уменьшилась;
* не создавать подстроки во время поиска (работать с индексами, копировать в конце);
* использовать порядковое (Ordinal) или побайтовое сравнение; никогда не использовать
  сравнение с учётом культуры.

### 10.3. Частые ошибки

1. **Использовать индекс начала вместо максимального индекса конца** для обратного
   поиска. Терминатор длины `L`, найденный в `maxEnd`, тогда перекрыл бы следующий
   сепаратор. Это самый вероятный источник несовместимости.
2. **Увеличивать счётчик сепараторов на каждой извлечённой переменной** вместо каждой
   части-сепаратора. Это ломает жадные переменные в шаблонах, начинающихся со
   статической части (Приложение C).
3. **Обрезать значение** или извлечённый текст, либо сравнивать без учёта регистра.
4. **Вставлять в карту** (`map.Add`) вместо присваивания (`map[name] = text`);
   повторяющееся имя допустимо и перезаписывается.
5. **Возвращать `null`/`nil`** или бросать исключение при «несовпадении»; возвращайте
   пустую карту.
6. **Требовать полного совпадения.** Замыкающие статические части — якоря, они не
   вырезаются, и префикс переменных может быть возвращён (§5.4).
7. **Сортировать или дедуплицировать альтернативы.** Порядок решает, кто победит при
   равенстве.
8. **Разбивать значение** вместо поиска сепараторов — так нельзя корректно реализовать
   жадные переменные (число разрешений заранее неизвестно).
9. **Игнорировать ведущую статическую часть.** Её нужно проверить как префикс значения и
   вырезать до нарезки первой переменной; иначе литерал молча становится частью первого
   извлечённого значения, а чужое значение объявляется совпадением (§5.1). Реализация,
   проходящая набор тестов, такую ошибку допустить не может — её ловят векторы
   `leading-static-part-*`.

## 12. Версионирование

Версия формата (`UFP-1.2`) нумерует синтаксис и поведение разбора. Она не зависит от
версии какой-либо библиотеки, но первая публикация вышла вместе с референсными
реализациями: формат `UFP-1.2`, библиотеки `1.2.0` (исправления поведения, вошедшие в
этот выпуск, перечислены в Приложении C).

Версия формата следует семантическому версионированию:

* **patch** — редакционные исправления и новые записи набора тестов, которые проходят
  сразу;
* **minor** — новый синтаксис или семантика, не меняющие результат существующих
  корректных шаблонов (например, новая необязательная метка);
* **major** — любое изменение, которое меняет результат существующего шаблона.

## Приложение A. Разобранные примеры

### A.1. Жадная переменная с двумя сепараторами

```text
значение: docs/reports/2024/annual_report.pdf     (35 символов, индексы 0…34)
шаблон:   <Path*>/<Filename>.<Extension>
```

Токенизация (§4): `V: Path (жадная)`, `S: /`, `V: Filename`, `S: .`, `V: Extension`,
следовательно `separators = ["/", "."]`.

Шаг 1 (§5.2), справа налево:

| k | Сепаратор | Граница до | `RFIND_WITHIN` | Граница после |
| --- | --- | --- | --- | --- |
| 1 | `.` | 34 | 31 | 30 |
| 0 | `/` | 30 | 17 | 16 |

Шаг 2 (§5.3):

| Часть | `separatorsSeen` | Терминатор | `positions[…]` | `cut` | Захвачено | `segmentStart` после |
| --- | --- | --- | --- | --- | --- | --- |
| `V: Path` | 0 | `/` | 17 | 17 (жадная) | `docs/reports/2024` | 18 |
| `S: /` | 1 | — | — | — | — | 18 |
| `V: Filename` | 1 | `.` | 31 | 31 (прямой поиск) | `annual_report` | 32 |
| `S: .` | 2 | — | — | — | — | 32 |
| `V: Extension` | 2 | — (финальная) | — | 35 | `pdf` | — |

Результат: `Path = "docs/reports/2024"`, `Filename = "annual_report"`, `Extension = "pdf"`.

### A.2. Частичное совпадение

```text
значение: x.png
шаблон:   <A>.<B>.jpg
```

`separators = [".", ".jpg"]`. Шаг 1: `positions[1] = −1` (`.jpg` отсутствует), поэтому
граница остаётся `4`; `positions[0] = 1`. Шаг 2: `A` завершается `.`, `positions[0] = 1`,
прямой поиск находит `.` в `1`, значит `A = "x"` и `segmentStart = 2`. `B` завершается
`.jpg`, `positions[1] = −1` → остановка с `A = "x"` (§5.4).

### A.3. Набор шаблонов

```text
значение:  1-2
набор:     <A>_<B>|<A>-<B>
```

* `<A>_<B>`: сепаратор `_` не найден → пустая карта (0 переменных).
* `<A>-<B>`: `A = "1"`, `B = "2"` (2 переменные) → побеждает.

Результат: `A = "1"`, `B = "2"`.

### A.4. Почему граница — максимальный индекс конца

```text
значение: xabab
шаблон:   <A*>ab<B>
```

Если ограничивать обратный поиск индексом **начала**, совпадение могло бы начинаться на
последнем символе и перекрывать следующий сепаратор. Терминатор `A` — `ab`, последнее
неперекрывающееся вхождение — индекс `3`, поэтому `A = "xab"` и `B = ""`. Реализация,
которая для этого значения вернёт `A = "x"`, использовала семантику индекса начала и не
соответствует спецификации.

## Приложение C. Изменения в референсной реализации 1.2.0

Последняя опубликованная версия, `1.1.0`, не компилируется и содержала три дефекта
разбора. Версия `1.2.0` — первая, реализующая эту спецификацию; она включает исправление
компиляции, подготовленное как `1.1.1` (так и не выпущенное), и три исправления поведения:

1. **Исключение при сепараторе в позиции 0.** Обратный проход безусловно вызывал
   `LastIndexOf(separator, searchEnd - 1)`. Если сепаратор был найден в позиции `0`, а
   левее ещё оставались сепараторы, `searchStart` становился `-1` и возникало
   `ArgumentOutOfRangeException`, например для `<A>_<B>_<C>` со значением `_x`.
   Спецификация требует считать такой сепаратор ненайденным (§5.2), что даёт пустой или
   частичный результат.
2. **Счётчик сепараторов увеличивался на каждой переменной.** Счётчик, которым
   индексировался массив найденных позиций, увеличивался после каждой извлечённой
   переменной, а не на каждой части-сепараторе. Для шаблона, начинающегося со статической
   части, счётчик указывал на «чужой» сепаратор: `<A*>_<B>` со значением `a_b_c` работал
   верно, а `_<A*>_<B>` со значением `_a_b_c` возвращал `A = ""`, `B = "a_b_c"` вместо
   `A = "_a_b"`, `B = "c"`, а некоторые шаблоны такой формы бросали
   `ArgumentOutOfRangeException` из `Substring`. В §5.3 счётчик определён как количество
   уже встреченных сепараторов — это и есть задуманное поведение, совпадающее с
   эквивалентным шаблоном без ведущей статической части.
3. **Ведущая статическая часть не проверялась и не вырезалась.** Статическая часть перед
   первой переменной игнорировалась, поэтому литерал попадал в извлечённое значение и
   чужие значения считались совпадением: `IMG_<Number>.jpg` возвращал
   `Number = "IMG_1234"` для `IMG_1234.jpg` и `Number = "scan_99"` для `scan_99.jpg`, из-за
   чего альтернативы набора шаблонов становились неразличимыми
   (`IMG_<Number>.jpg|scan_<Number>.jpg`). Теперь §5.1 требует, чтобы значение начиналось
   с ведущей части, и вырезает её: тот же шаблон даёт `Number = "1234"`, а для
   `scan_99.jpg` — пустой результат.

Во всём остальном поведение проверено как идентичное опубликованному: набор тестов на
соответствие (§11) проходит на обеих реализациях, а 14 000 случайно сгенерированных пар
(шаблон, значение) — включая некорректные шаблоны, пустые значения, перекрывающиеся
сепараторы, метки жадности и несколько альтернатив — дают одинаковый результат в
референсных реализациях и в Python-порте [`src/UFP.Python/ufp.py`](../src/UFP.Python/ufp.py),
написанном по §4–§6 этого документа, который использовался для генерации набора тестов
(Python индексирует строки по кодовым точкам, .NET — по единицам UTF‑16, так что эти два
порта дополнительно подтверждают §10.1).

Других отличий нет, и поведение ни одного корректного шаблона, начинающегося с
переменной, не изменилось.
